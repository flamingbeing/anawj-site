# NUH Roster: improvement review (13 Oct 2026)

Twenty read-only reviews of the app, one area each, done in one sitting. Nothing here is built or agreed yet: the
owner picks from it (STATUS.md › Next). Line numbers are from main at `60ce030` and will drift. Spot-checked before
saving: silent local save (`js/app.js:152`), `today()` is tomorrow (`app.js:21`), `editor()` is "role is not viewer"
(`firestore.rules:21`), ExcelJS loads on every page (`index.html:61`), and double cover with no junior is only a
generator note (`js/engine.js:562`).

Effort: S (hours), M (a day or two), L (several PRs). Impact: high, med, low.

## Recommended order

Safety first, then the jobs people do every day, then new things.

**Batch A: don't lose work, don't miss a danger** (mostly S)
1. **Warn when the browser stops saving.** `save()` swallows every error and `state.days` is never pruned, so a full
   localStorage stops saving with no message. Show a lasting bar ("not being kept in this browser: Download
   everything"); stop storing `checks` in each day; offer to clear old days already saved to the team; ask
   `navigator.storage.persist()`. Found by four reviews (errors, performance, save/sync, data).
2. **Keep a copy of damaged saved data** before starting fresh (`app.js:44-48` overwrites it on the next save).
3. **Live check: double cover with no junior.** Only the generator notes it (`engine.js:562`); after a hand edit the
   Problems card can say "No problems found" on that roster. Add it to `check()` as an error with a fill fix.
4. **Live checks: one person in two columns, a senior on 3 or more rooms, someone on an admin day put on a list.**
5. **Firestore rules: an allowlist of roles.** `editor()` is role ≠ viewer, so a typo or blank role makes an editor.
   Use `role in ['admin','rosterer']`; check member documents' shape; stop an admin removing their own entry.
   Check that `updatedBy.email` is the signed-in user. (A rules PR: waits for the owner's OK before merging.)
6. **Emulator tests for the roster rules** in `tools/test-rules.sh` (viewer can read but not write, editor can't
   write members, versions can't change), so item 5 and the viewer path are tested without signing in.
7. **Team documents: the last save wins.** `saveTeam`, `saveMonthly` and `saveRotations` replace the whole document
   with no conflict check or history (rosters already have both). Copy the roster pattern (`expectedUpdatedAt`,
   transaction, versions).

**Batch B: the 7am view for staff** (S–M)
1. **My day opens on today in the morning.** `today()` is always tomorrow, so a viewer at 7am lands on "isn't out
   yet". Before a cut-off (say 2pm) open on today; add Today / Tomorrow buttons.
2. **"Saved by X at 06:42" and "changed since you last looked"**: refresh when the page comes back into view; show
   only the changes to that person's lines.
3. **My week**: the next 5–7 days in one strip (saved rosters, else leave, calls and posting).
4. **Add to calendar (.ics)** built in the browser; no feed URL until PDPA approval.
5. **Copy for logbook** on a room line (date, room, senior, case notes): a first, safe step toward the APMES bridge.
   Put the facts in one tested `dayFacts()` in `engine.js` that My day, .ics and copy all use.
   Before 3–5: tie a member to a staff id; today My day matches the member's name fuzzily.

**Batch B2: a faster morning for the rosterer** (S–M)
1. **Open on tomorrow** when the saved date is in the past (today the bar only warns "Not tomorrow"), with a toast
   to go back.
2. **One "Save and send"** for members: save for the team, then the remembered format (e.g. the WhatsApp image).
3. **"Until <date>" on a hand-set status or comment** (admin, a course), carried into new days marked `auto` so a
   hand change still wins.
4. **"Start from last <weekday>"**: which rooms run, sessions and fixed people (not case notes).
5. **"Start from <previous date>"**, then live checks and Fill gaps swap out people now on leave or post call.
   Risk: anything carried forward can put someone on the roster who isn't there; every carried value needs a visible
   `auto` mark and Undo, and the monthly rosters and live checks win.

**Batch C: sending changes** (S–M)
1. **Changes since sent**: keep a copy of the rows when sent; list who moved and which rooms changed; "Send changes"
   shares the image with the list as the message.
2. **Only count a send that happened** (a cancelled share or a failed PDF still marks the day as sent, `app.js:3079`).
3. **"Updated 09:15" on a resent sheet** so two images of the same day can be told apart.
4. **A readable WhatsApp image**: draw at 2x and offer "in 2 images" (rooms, then calls and clinics), each under
   1600px tall; shrink single-line text that overflows its cell.

**Batch D: phones and keyboards** (S–M)
1. **Inputs at 16px on phones** (iOS zooms on anything smaller, then the page scrolls sideways).
2. **Bigger tap targets** (`.add-name`, `.name`, `.chip`, `button.small` are about 20px tall).
3. **Keep the bottom sheet above the keyboard** (`visualViewport`, sticky Save bar, toast above the sheet).
4. **Cases tab as cards on phones** (it's a 7-column table, the first daily step).
5. **Keyboard access to people**: chips are spans with onclick only; make them buttons, give the person box
   `role=dialog`, focus in and back out; problem rows get "Error:/Check:/Note:" words, not just colour.

**Batch E: imports that don't fail quietly** (M)
1. **One fix-names step after any import**: each unmatched or ambiguous name with a ranked picker; picking saves the
   spelling as a short name and re-applies.
2. **Preview before a monthly roster replaces the stored one** (columns found and missing, people unmatched), with
   Undo instead of the confirm boxes for import, replace and clear.
3. **Find draft columns by heading**, not fixed letters (`xlsxio.js:18-26`); parse the date with a fixed format.
4. **Read every sheet of an Excel monthly roster**, not only the first.

**Batch F: planning ahead in Monthly** (M)

2. **Which rosters are loaded** this month and next (six chips each); missing ones in the Steps strip.
3. **Leave per day**: count of seniors and juniors away, with a settable limit.
4. **Rotation counts per posting per week**, and "start next year from this year's pattern".
5. Saved future days keep old leave and post-call statuses after a monthly roster changes; flag them.

3. **A practice draft to download**, so "Do it all" can be practised.
4. **"Fix these 3 problems"** exercise with a ticking checklist; scenario presets (short-staffed, weekend, late MC)

- Run `check()` and `save()` only when something changed, not on every render; filters hide rows instead of

- Plain messages for offline, timed-out and signed-out cloud errors; a catch-all error message with "press Undo".

- Design: one highlight colour and one focus ring as variables; four type sizes; a test that `style.css` still

## Lessons from the review

- **The biggest risks are silent ones**: browser storage filling up, team documents overwritten by the last save, a
  monthly import missing a renamed column, "No problems found" after a hand edit. Fix those before adding features.
- **Rules changes deploy live with no tests.** Add the emulator suite before the next rules change.
- **No XSS sink**: every element is built by `h()` with `textContent`; keep it that way (never `innerHTML`).
- **My day trusts a fuzzy name match.** Link members to staff ids before building more on it.
- **Practice and the tour can drift from the real app unnoticed**: test that every tour selector exists and that the
  demo day generates with no errors.
- **Per-person history is personal data.** Counts built from free text can be wrong; limit them to rosterers and admins
  and wait for the PDPA approval.
